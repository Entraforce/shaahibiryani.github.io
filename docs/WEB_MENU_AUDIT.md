# Website menu — audit, baseline and what changed (Phase 2W)

Written 2026-08-27. The app menu phase (`ux-menu-v1`) came first; this is its
counterpart on the live site, where real payments already happen.

---

## 1. How the website menu is actually built

The most important thing to know before editing it, and not obvious from reading
`index.html`:

**The menu is generated. It is not hand-written.**

```
web_menu_categories ┐
web_menu_items      ├─→ publish-menu (edge fn) ─→ render-menu.js ─→ index.html
web_menu_cards      ┘        ▲                                         │
                             │                                         ▼
                     owner presses Publish                    committed to GitHub
                          in /kadmin                          → live in ~1 minute
```

Five regions are rewritten on every Publish:

| Region | Marker | Contains |
|---|---|---|
| Menu | `<!-- GEN:MENU -->` | category tabs + every item row |
| Splash | `<!-- GEN:SPLASH -->` | bestseller price list |
| Cart id map | `var PID_MAP={…}` | dish name → server price id |
| Schema | `"hasMenuSection"` | Google structured data |
| Cards | (patched per `data-name`) | bestseller card prices |

**Anything hand-edited inside those regions is reverted by the next Publish.**

That had already happened twice, silently:

- `e0252a7` added alt text to 83 menu photos — the renderer still emitted `alt=""`.
- `c9fd835` added real `width`/`height` to the same 83 photos — the renderer
  emitted neither.

Both were accessibility and layout-stability fixes sitting one owner click away
from being wiped, and nothing compared the two files. Proven by rendering the
live data through the committed renderer: output differed from the committed HTML
on exactly 83 lines, all of them those attributes, and matched byte-for-byte once
those were normalised away.

**Fixed by** teaching the renderer to emit both, and adding
`scripts/render-index.mjs --check`, which fails if `index.html` ever stops being
what the renderer produces.

### Where each part lives

| Concern | Lives in | Regenerated by Publish? |
|---|---|---|
| A. Menu presentation | `render-menu.js` + CSS/JS in `index.html` | rows/tabs YES, CSS/JS no |
| B. Cart state | `cart` array + `renderCart()` in `index.html` | no |
| C. Checkout / payment | `create-web-order`, `confirm-web-order`, `prices.ts` | no — server-side |
| D. Ask Shaahi | `#chat-bubble` + scripted replies in `index.html` | no |
| E. Unrelated | hero, about, catering, testimonials, FAQ, Clover drawer | no |

### The sideways scroll

Not the menu — the bestsellers carousel *controls*. Fourteen 20px dots in a
no-wrap flex row measured 428px inside a 326px container, so the ← arrow sat at
`x=-79` and the → arrow ended at `x=469` on a 390px screen. Both unreachable, and
the whole page — menu included — drifted sideways.

## 3. What changed

### Data integrity (Phase 0, website side)
`web_menu_items` has **no dietary or spice columns at all**, so the site had never
shown a vegetarian mark or a spice level. Nothing to suppress — but also no way to
tell a guest which dishes are vegetarian.

The verified list is now derived from the app's authoritative `lib/menu-data.ts`,
joined on the pid, and re-checked against each dish's own description with the
same rule the app uses (`scripts/build-menu-facts.mjs` → `menu-facts.js`).
Result: 30 dishes carry a leaf + the word VEG. Lukhmi and Patthar Ka Gosht carry
nothing — the app data now says they are not vegetarian, and their own copy says
meat.

Beverages are excluded from the mark on purpose: a bottle of water is vegetarian,
but badging it is clutter, and a menu covered in badges stops communicating.

Spice: no verified spice data exists anywhere, so still nothing is shown.

### Names a guest reads vs names the system uses
`web_menu_items.name` is the identity key for the cart, `PID_MAP` and the kitchen
ticket, and it is UNIQUE — so eight rows have a badge word baked into the identity
itself: `Zafrani Mutton Signature`, `Goat Marag Check Avail.`,
`Lukhmi 2pc Check Avail.`, `Butter Chicken Popular`, and four more.

Those strings were reaching the customer: in the item dialog title, on the cart
line, and in `itemName` on the order sent to the kitchen.

Rows now carry **both**: `data-name` (identity, untouched) and `data-label` (what
anyone reads). All 141 rows still resolve to a server price id — verified row by
row, including all eight badge rows.

### Everything else

| Phase | Change |
|---|---|
| 6 | Category nav: one scrolling row, sticky under the header, 47px at every width |
| 7 | Menu search over name, group, category and description; clear control; no-result state |
| 8 | 84px photography (was 56px); price given its own column; the row is the target |
| 9 | Verified vegetarian mark only; no vegan/GF/allergen claims invented |
| 10 | No spice indicator — no verified spice data exists |
| 11 | Branded placeholder for photo-less dishes, never a stand-in dish |
| 12 | Dialog is `role="dialog" aria-modal`, Escape closes, focus trapped and restored |
| 13 | Add to cart no longer force-opens the drawer; toast + count confirm it |
| 14/15 | Concierge context (category, query, item) in frontend state; one invitation per category |
| 16 | Concierge 201×48 named control vs 44×44 WhatsApp; no overlap |
| 18 | Rows are `role="button" tabindex="0"`; tabs are a real tablist with arrow keys |

## 5. Known, not fixed here

**The hero slideshow ships 8.9MB of PNG.** Four images at the repo root
(`2386FC84….PNG` and three siblings, 2.1–2.4MB each) are CSS backgrounds in
`#hero`, so they cannot be lazy-loaded and all four download before a guest sees
anything. By far the largest performance cost on the site, and pre-existing. Left
alone deliberately: hero content, not menu, and replacing the homepage's most
prominent images deserves its own change rather than a line in a menu commit.
WebP at display size would likely save 8MB+.

**The website's "Ask Shaahi" is not the AI concierge.** It is a scripted
decision-tree bot; the page makes no AI call at all — the real Claude concierge
runs only in the mobile app — yet it is branded "AI Dining Concierge". Menu
context is now available to it in frontend state, but wiring it to the real
concierge function is an architecture change and was not made.

**Sold-out dishes vanish rather than showing as sold out.** `available=false`
removes the row entirely (6 items today: 4 appetizers plus Goat Marag). There is
no "sold out" state to style. Whether a guest should instead see a greyed-out
dish is a product decision for the owner.

```bash
node scripts/build-menu-facts.mjs     # after new photos or app dietary changes
node scripts/render-index.mjs         # regenerate the generated regions
node scripts/render-index.mjs --check # CI-style guard: fails if index.html is stale
```
